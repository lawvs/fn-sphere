Start with the default schema matching and input adapters. Add configuration when the product needs different behavior.

## Organize by Responsibility

Keep the integration entry point focused on configuration and data consumption. As the implementation grows, separate the schema, theme, and localization:

```text
filter-sphere/
├── index.tsx   # Hook, provider, builder, and filtered results
├── schema.ts   # Data schema and optional rule defaults or filter functions
├── theme.tsx   # Theme overrides
└── locale.ts   # Translation configuration, when needed
```

Expand a module into a directory when it contains distinct responsibilities, such as several input components or multiple translation dictionaries. Keep short helpers near their only caller. Export the interface that consumers need, and keep implementation details private.

## Start with Schema Defaults

Filter Sphere discovers compatible operators from the schema. With no `filterFnList`, `useFilterSphere` uses the preset functions.

```ts
// schema.ts
import { z } from "zod";

export const filterSchema = z.object({
  id: z.number(),
  name: z.string(),
  age: z.number(),
});

export type Person = z.infer<typeof filterSchema>;
```

Without a description, field labels use their paths, such as `name`. Literal input options use their values as labels. Both pass through `getLocaleText`.

If a field needs a different display label or translation key, add `.describe()`, such as `z.string().describe("person.name")`. Custom label consumers must use the same mapping as the field selector. See [Localization](/fn-sphere/customization/localization/) and [Schema Metadata](/fn-sphere/customization/schema-metadata/).

If the product needs a restricted operator list or custom behavior, set `filterFnList`. Presentation changes alone do not require a separate operator whitelist. See [Customizing Filters](/fn-sphere/customization/filter/).

## Override the Relevant Theme Layer

Use `createFilterTheme` to merge overrides with the defaults. Choose the layer that owns the change:

| Change                                   | Theme layer      |
| ---------------------------------------- | ---------------- |
| Control appearance or interaction        | `components`     |
| Layout of rules and groups               | `templates`      |
| Mapping parameter schemas to input views | `dataInputViews` |
| Underlying HTML elements                 | `primitives`     |

Built-in adapters supply values and options to controls. For example, changing `components.MultipleSelect` retains the built-in array matching and argument updates. A custom `dataInputViews` entry is useful when the existing adapters cannot represent the parameter shape.

```tsx
// theme.tsx
import { createFilterTheme } from "@fn-sphere/filter";

export const theme = createFilterTheme({
  components: {
    Input: ({ onChange, ...props }) => (
      <input
        {...props}
        className="filter-input"
        onChange={(event) => onChange?.(event.target.value)}
      />
    ),
  },
});
```

The component `Input` receives a string callback, while the HTML input emits an event. Custom components must preserve this contract.

When a template renders other templates, read them with `useView("templates")`. This lets overrides apply to nested groups as well. See [Theme](/fn-sphere/customization/theme/) for a recursive example.

## Use One Translation Entry Point

Keep translation lookup in a locale module. Extend a built-in locale with application labels, and provide a fallback for missing keys.

```ts
// locale.ts
import { defaultGetLocaleText } from "@fn-sphere/filter";
import { zhCN } from "@fn-sphere/filter/locales";

const messages: Record<string, string> = {
  ...zhCN,
  name: "姓名",
  age: "年龄",
};

export const getLocaleText = (key: string): string =>
  messages[key] ?? defaultGetLocaleText(key);
```

Inside the provider, custom UI can access `getLocaleText` through `useRootRule()`. If the application already uses an i18n library, connect its translation function to this interface. See [Localization](/fn-sphere/customization/localization/) for language selection and configuration factories.

## Show the Filtering Result

The entry point connects the modules and applies the predicate to data. This example uses a list so that it works without a table component.

```tsx
// index.tsx
import {
  FilterBuilder,
  FilterSphereProvider,
  useFilterSphere,
} from "@fn-sphere/filter";
import { filterSchema, type Person } from "./schema";
import { theme } from "./theme";
import { getLocaleText } from "./locale";

const data: Person[] = [
  { id: 1, name: "Alice", age: 25 },
  { id: 2, name: "Bob", age: 30 },
];

export function MyFilter() {
  const { context, predicate } = useFilterSphere<Person>({
    schema: filterSchema,
    getLocaleText,
  });

  return (
    <FilterSphereProvider context={context} theme={theme}>
      <FilterBuilder />
      <ul>
        {data.filter(predicate).map((person) => (
          <li key={person.id}>
            {person.name}: {person.age}
          </li>
        ))}
      </ul>
    </FilterSphereProvider>
  );
}
```

If the demo needs initial conditions, define them with the rule constructors and pass the result as `defaultRule`:

```ts
import { createFilterGroup, createSingleFilter } from "@fn-sphere/filter";

export const defaultRule = createFilterGroup({
  op: "and",
  conditions: [
    createSingleFilter({ path: ["age"], name: "greaterThan", args: [25] }),
  ],
});
```

## Keep Examples Focused

A filter example must show how editing a rule changes the data results. In this repository, reuse the existing `Table` component when a table helps demonstrate that behavior.

Keep layout, language controls, and rule previews in supporting components so that the entry point explains the library integration. Choose names that describe each component's role. Directory names already provide context, so files such as `theme/inline-input.tsx` and `locales/messages.ts` need no additional example prefix.

When adapting a visual reference, carry over the interactions needed for filtering. Add workflow actions, history, or other supporting features only when the example needs to demonstrate them.

Check field and operator changes, argument editing, and the resulting data. For nested rules, also check group editing and template overrides. For localization, check that labels change while stored rule values stay the same.
